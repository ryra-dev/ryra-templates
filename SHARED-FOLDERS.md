# Shared folders

One machine can host several named spaces. Each person keeps their own account,
home, agent sessions and credentials, with shortcuts to shared content:

```text
/home/alice/Shared/Company  -> /srv/shared/company
/home/alice/Shared/Research -> /srv/shared/research
/home/bob/Shared/Company    -> /srv/shared/company
```

Enable spaces in the machine's `configuration.nix` or a local module:

```nix
{ ... }: {
  ryra.sharedFolders = {
    company = {
      label = "Company";
      members = [ "alice" "bob" ];
    };
    research = {
      label = "Research";
      members = [ "alice" ];
    };
  };
}
```

Members are existing personal Linux accounts, such as those generated by Ryra's
login module. This option does not create accounts or grant SSH, sudo, access to
an agent session, or credentials. Organization invitation/group changes still
need to be translated into this member list and deployed; templates cannot read
live organization membership on their own. New Ryra versions also accept
`[[shared_folders]]` in `organization.toml`, with `name`, `machine`, optional
`label`, and `access` group names. Their generated login module derives this
option's member lists from active people with personal machine access.

The attribute name is a stable storage identifier: `company` means
`/srv/shared/company` and Unix group `ryra-shared-company`. Use up to 20 lowercase
letters, digits or hyphens, starting with a letter. `label` is the shortcut's
friendly name and defaults to the identifier. Labels must be unique. Choose
meaningful names such as `company`, `research` or `client-acme`, rather than
numbered copies of `shared`. Nothing is enabled by default.

Directories are root-owned, setgid and accessible to their group (`2770`).
Default POSIX ACLs let normally created files and subdirectories inherit group
write access, including when a member's usual umask is restrictive. Each space
has its own group. `/srv/shared` allows traversal without listing all spaces.
Root and machine administrators can access the content.

Shortcuts are created on boot and configuration activation, after the storage
and home mounts are available. Existing files, directories and different
symlinks at a shortcut's location are preserved. If a name is already occupied,
choose another label or move that item yourself. Keep `~/Shared` as a directory;
the module does not replace it with a link to everybody's spaces.

Changing an identifier creates a new storage location; it does not move data.
Removing a space, label or member does not delete its documents or old home
shortcuts. An obsolete shortcut can be removed manually. Access comes from the
target directory's group, not the presence of a shortcut. Group changes require
fresh login sessions, including restarting agents. Withdrawing access from an
already running session requires ending that session; removing a member does
not erase copies they already have.

Existing contents are not recursively repaired. Files moved from elsewhere,
copies that preserve permissions, programs requesting mode `0600`, and later
`chmod` calls can restrict collaboration. Filesystem permissions do not merge
concurrent writes or provide revision history. Validate the actual editors and
agents used by the team. Members can rename or delete entries in shared writable
directories.

Back up `/srv/shared` separately, with versioning and a tested restore. Home
backups that do not follow symlinks will not include it. The templates' existing
`/home` and `/var/lib` deployment snapshots do not cover these documents. No disk
layout or persistent mount is changed by enabling this module; configure storage
explicitly if the machine uses an ephemeral root or a separate data volume.

Validation:

```sh
python3 tests/check_shared_folders.py
# Apple Silicon macOS with Lima; creates and deletes its own isolated test VM.
python3 tests/check_shared_folders_vm.py
```

The Linux test uses distinct accounts to check actual shared writes, denied
access, permission inheritance, existing shortcut collisions and membership
removal. It exercises the evaluated tmpfiles rules without deploying a machine
configuration or changing existing VMs.

Ryra Files collaborates directly on accessible text files. These templates
provision folders and permissions; they are not required for live editing.
